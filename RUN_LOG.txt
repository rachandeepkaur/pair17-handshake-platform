Lab 2 — Kafka event pipeline: happy path and three failure cases
==========================================================================

Date:     2026-11-13
Stack:    docker compose (Kafka 3.8.0 KRaft, MongoDB 7.0, MySQL 8.0), branch feature/company
Command:  scripts/kafka_demos.sh        (cases 0-3, output below verbatim)
Workers:  p17-application-worker, p17-event-worker, p17-job-worker
          consumer groups p17-<worker>, enable.auto.commit=false,
          WORKER_MAX_ATTEMPTS=3, backoff 0.5s, 1s

Delivery design (backend/app/workers/runtime.py)
- At-least-once: the worker commits a message's offset only AFTER its MongoDB
  write succeeded, or after the message was copied to the dead-letter topic.
- Idempotent consumers (backend/app/workers/handlers.py): every insert uses a
  deterministic _id (the event_id, or registration-<id> / the job_id business
  key), so a duplicate becomes a DuplicateKeyError that is logged as "already
  applied; skipped". Counts are recomputed with count_documents + $set, never
  incremented.
- Poison messages: up to 3 attempts with exponential backoff, then the original
  bytes go to "<topic>.dlq" with x-error / x-attempts / x-original-* headers and
  the offset is committed, so the partition keeps moving.
- MongoDB outages are not treated as poison: the worker retries the same
  message every 5s without committing or dead-lettering it.

(tests/test_kafka_events.py covers retries, the DLQ decision and idempotency.)

Findings
--------
Case 0 (happy path). Five API calls through the gateway published all five
topics (application.created, application.updated, application.status_changed,
event.registration_created, job.created). Each worker received its message,
wrote MongoDB (application_events, notifications, event_registrations /
event_stats, job_search_index) and committed the next offset.

Case 1 (duplicate publish, same key). The identical message was produced twice
on application.created with the same key, so both copies landed on the same
partition (offsets N and N+1). The first was written; the second hit the
existing _id = event_id and was skipped. MongoDB holds exactly one document
for the event_id, and both offsets were committed (LAG 0): the duplicate was
consumed, not left behind.

Case 2 (worker killed during processing). The worker wrote MongoDB and was
SIGKILLed during its 30 s pause before the commit. While it was down, the
document existed but the group's committed offset was one behind the log end
(LAG 1). On restart, Kafka redelivered that same offset: the event was
REPROCESSED, not lost. The idempotent write recognised it ("already applied;
skipped"), the offset was then committed, and MongoDB still has one document.
Had the kill come before the write, the redelivery would simply have performed
the write for the first time, so the event is not lost in either position.
Redelivery came about 40 s after the kill (09:09:21 vs ~09:08:40) because the
group coordinator waits for the killed member's session to expire
(session.timeout.ms, default 45 s) before reassigning its partitions.

Case 3 (poison message). A non-JSON value was produced on
application.status_changed, followed by a valid event with the same key, so it
sat directly behind the poison on the same partition. The worker failed the
poison 3 times (backoff 0.5 s, 1 s), copied it unchanged to
application.status_changed.dlq with the error and original position in its
headers, committed its offset, and processed the valid event in the same second: the
pipeline continued after the failed message was isolated.

Known limitation. APIs publish after the MySQL commit; if Kafka is down at that
moment the API call still succeeds and the event is only logged as unpublished.
A transactional outbox table relayed to Kafka would close that gap.
